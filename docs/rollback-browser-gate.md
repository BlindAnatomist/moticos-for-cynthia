## Publication and invocation

Stage the exact reviewed public tree on `staging/rollback-browser-gate-20261005`, which matches no workflow push trigger. After public-tree readback and separate execution approval, push that same tree to the sole trigger `verify/rollback-browser-80-20261005`. Do not open a PR as part of this gate: the historical quality workflow has its own PR trigger. No merge, deployment or release is included. Publication must use this sanitized tree, without checkpoint directories or local Git history.

The sole new workflow is `.github/workflows/verify-rollback-browser.yml`. It accepts only its exact push branch, only run attempt 1, standard `ubuntu-latest` runners and read-only repository permissions. It cannot dispatch, merge or deploy. The owner's confirmed automatic zero-dollar stop stays enabled. A spending-stop block means stop and notify, with no budget change or paid overage. A rerun or changed tree requires a new decision.

Read-only collection uses `npx playwright test --config=playwright.rollback.config.js --list --reporter=json`, optionally followed by exactly one `--project=NAME`. Execution uses exactly `MOTICOS_ROLLBACK_BROWSER_APPROVED=1 npx playwright test --config=playwright.rollback.config.js --project=NAME`. NAME is one of `chromium-desktop`, `webkit-iphone-13`, or `webkit-iphone-large`. The flag is an operator guard, not independent permission. Filters, retries, repetitions, extra reporters, multiple profiles and budget overrides outside eight to nine minutes are rejected. A real installed Playwright IPC worker inherits only the previously validated command. Three worker-only fixtures test this without starting a browser or server.

## Scope, time and evidence bounds

One build job has a seven-minute cap. Three sequential browser profiles each have a fifteen-minute job cap: at most 52 runner minutes. Each profile gets eight to nine browser minutes only when three further minutes plus fifteen seconds remain for evidence handling. Insufficient time prevents browser launch. Ordinary cases allow 120 seconds; the four-record recovery case allows 180 seconds. Each failure observation is bounded externally to five seconds; at most four observations add twenty seconds, with a 25-second hook allowance still inside the global cap. These budgets are deliberately above a prior 64.1-second collection sweep; a 60-second aggregate case cap was inadequate. There is one worker, no retries, no skipped acceptance case, and the first failing case stops that profile. Other profiles may still collect independent evidence.

The focused supplement retains sixteen cases per profile, 48 total. It requires 189 explicit viewport screenshots, 24 native complete JSON downloads and 24 native 1536×1120 representative postcard PNGs, plus 48 per-case observation journals. All four preserved records must be visible with families, discoveries, named board positions and complete 100-history JSON. Every playable envelope decodes all ten actual collection artworks per profile. The eight postcard samples span tiers 3, 4 and 5 and both original and accepted batch paths. This does not claim all historic postcard compositions or physical-iPhone Safari were rerun.

Automatic traces retain action/source information on failure with screenshot screencasts, DOM snapshots and attachment duplication disabled. Explicit required screenshots and downloads remain full fidelity. Separate failure state, viewport PNG, accessibility context, before/after modal checks, image-decode journals, native filenames and content validation provide diagnosis. Observations are sequential rather than an atomic DOM-to-pixel snapshot.

The upload ceiling is 32 MiB preflight plus three profiles of 98 MiB each: exactly 326 MiB (341,835,776 bytes). A profile may upload two complete 45 MiB parts, plus one independent 8 MiB diagnosis. Caps include repeated manifests and conservative ZIP framing allowances. Every artifact expires after one day. The one production build is inside the preflight artifact and is restored by each profile. Both packers restore and hash-check every member before upload. The complete profile packer uses lossless whole-file SHA-256 deduplication; it never drops, truncates, downscales or converts a required file. Deduplication alone does not rescue a bloated trace, so trace capture is minimized at generation. Any over-budget complete package fails the gate. Diagnosis remains explicitly incomplete and cannot substitute for complete raw evidence.

## Frozen authority and acceptance

`rollback-authority.json` pins every runtime source, accepted asset, dependency lock and build file without private provenance. `rollback-browser-contract.json` pins exact case IDs, profile sizes, native samples and required artifacts. `rollback-frozen-inventory.json` pins the complete public source, harness and workflow file set and hashes, excluding only itself; its own SHA-256 is carried in the run identity and the externally reviewed publication manifest. CI never regenerates any inventory. The server rechecks source and build before serving.

After retrieval, restore the preflight with `python3 scripts/restoreCollageEvidence.py --parts PARTS --out NEW_DIRECTORY`. Restore each profile with `python3 scripts/contentAddressedEvidence.py restore --parts PARTS --output NEW_DIRECTORY`. Put the three restored profiles under a common directory named by profile and run `node scripts/verifyRollbackCoverage.mjs aggregate DIRECTORY`. This rechecks every source identity, terminal event, complete native JSON content, PNG dimensions, decoded image and screenshot journal, and every attachment hash. Require all 48 unique zero-retry terminal passes. Then inspect all screenshot and actual postcard pixels and record the review separately. Machine success remains `passed-awaiting-content-review`; no file is automatically marked visually accepted.

Synthetic saves only. Existing player data, billing settings and deployed sites are outside this gate. Browser execution, native downloads and visual acceptance remain unverified until the approved run and artifact review complete.
